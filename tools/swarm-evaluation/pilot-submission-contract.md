# Pilot submission templates

Prepared before comparative model runs. These templates add no task clues and
do not alter the four frozen packets. The controller must record the exact
instantiated UTF-8 input hashes and versioned capability/setup evidence before
each arm. No comparative run has started. Native readiness and completion-observer
verification remain gates in the evaluation protocol.

## Neutral initialization: every fresh main harness

This is a fresh session being prepared for a task. Wait for the task instruction
before inspecting project files or starting task work. No task action is needed
during initialization.

## Common task instruction: every main harness

Read README.md and complete the task in this repository. Use your normal tools,
iterate and verify your work as appropriate, and submit the deliverable requested
by the task. Work from the supplied task materials; do not seek reference solutions,
grading/evaluation files, other task runs or unrelated conversations. Keep task
file changes inside this repository. Do not change global settings or existing user
sessions. Preserve anything needing removal in a retired folder instead of deleting
it. Give your normal final response when you have finished the task.

## Pair-only process introduction

You and the other explicitly connected session have the same complete task and
share this task repository. Communicate through TermX or inspect authorized peer
context when you judge it useful. Decide how to coordinate yourselves. There is
no required exchange; productive silence is allowed.

## Controller application

The solo receives only the common task instruction after neutral setup. Each
pair participant receives the same common instruction followed by the same
pair-only introduction. Existing task README contents supply all requirements;
no additional clues, leader/role assignments, debate schedule, required messages,
mandatory summaries or model/token quotas are appended. Normal harness-internal
delegation remains available where it ordinarily is, with capability and usage
coverage recorded. The experiment's observation window is separate from product
conversation behavior.

Capture the first task-submission time, each participant's submission time and
dispatch skew. Use the protocol's verified native completion and snapshot rule,
not an inactivity guess or a hidden-grader result. Do not send follow-up coaching
or owner-composer messages after submission. Record ordinary permission handling
and operational interruptions without silently repairing a run in place.
